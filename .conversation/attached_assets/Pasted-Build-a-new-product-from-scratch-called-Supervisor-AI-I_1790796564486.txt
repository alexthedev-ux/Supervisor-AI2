Build a new product from scratch called "Supervisor AI".

IMPORTANT:
This is a completely independent implementation.

Do NOT use, copy, recreate, or assume any existing implementation from another project or coding agent.

Design the architecture yourself based only on the product specification below.

The goal is to build a working MVP, not a static mockup.

==================================================
PRODUCT
==================================================

Supervisor AI is an AI orchestration and control system that sits ABOVE AI coding agents.

The user gives Supervisor a software development task.

Supervisor manages one or more AI coding agents and makes sure the task actually gets completed and validated.

The core concept is:

USER
  ↓
SUPERVISOR AI
  ↓
CODING AGENT / WORKER
  ↓
CODE
  ↓
TESTS / BROWSER / VALIDATION
  ↓
RESULT
  ↓
SUPERVISOR
  ↓
DONE / RETRY / ESCALATE
  ↓
ANOTHER AGENT IF NECESSARY

The Supervisor is NOT primarily the coding agent.

Its main responsibility is orchestration, verification, state management, recovery and intelligent routing.

==================================================
CORE PROBLEM
==================================================

AI coding agents can write code, but they can also:

- misunderstand requirements;
- introduce bugs;
- get stuck in loops;
- repeatedly fix one problem while creating another;
- claim a task is finished when tests still fail;
- waste large amounts of tokens;
- waste cloud money;
- lose useful context;
- fail halfway through a complex task.

Supervisor AI exists to control this process.

The Supervisor should determine:

"Is the task actually finished?"

not simply:

"Did the coding agent say it is finished?"

==================================================
MAIN WORKFLOW
==================================================

A user creates a task:

Example:

"Fix the authentication problem in my application."

Supervisor should:

1. Receive the task.
2. Understand the goal.
3. Create a task state.
4. Select a Worker.
5. Give the Worker the task.
6. Monitor the Worker.
7. Receive the Worker result.
8. Validate the result.
9. Decide what happens next.
10. Repeat when necessary.
11. Escalate when the current Worker is no longer effective.
12. Create checkpoints before important transitions.
13. Resume from checkpoints when another Worker takes over.
14. Finish only when validation succeeds.

==================================================
SUPERVISOR DECISION ENGINE
==================================================

Supervisor must make explicit decisions.

Possible states:

PLANNING
RUNNING
VALIDATING
RETRY
ESCALATING
CHECKPOINTING
RESUMING
DONE
FAILED
PAUSED

The Supervisor should never rely on arbitrary strings scattered throughout the application.

Use an explicit state machine or equivalent robust state-management system.

The decision engine should consider:

- Worker result;
- test results;
- browser validation;
- repeated errors;
- progress;
- attempts;
- token usage;
- cost;
- task complexity;
- configured policies.

==================================================
RETRY
==================================================

When a Worker fails, Supervisor may retry.

Example:

Attempt 1
FAIL

Supervisor:
RETRY

Attempt 2
FAIL

Supervisor:
RETRY

Attempt 3
SUCCESS

Supervisor:
DONE

Retry limits must be configurable.

Track separately:

total attempts
failed attempts
successful attempts
retry count

Never count an attempt twice.

==================================================
LOOP DETECTION
==================================================

This is a critical feature.

Supervisor should detect when an agent is stuck.

Examples:

Same error repeated.

Same files modified repeatedly.

Same test failures repeatedly.

Agent reports success but validation still fails.

No meaningful progress across several attempts.

The Worker produces substantially identical results.

When a loop is detected:

STOP the Worker.

Create a checkpoint.

Analyze the situation.

Then either:

RETRY with better context

or

ESCALATE to another Worker.

==================================================
ESCALATION
==================================================

Escalation means transferring the task to a stronger or different agent.

Example:

Local Worker:
9B

Attempts:
3

Result:
still failing

Supervisor:

ESCALATE

Cloud Worker:
stronger model

The new Worker must receive enough state to continue the task.

Do NOT simply send the entire previous conversation blindly.

Instead provide a structured checkpoint.

==================================================
CHECKPOINT SYSTEM
==================================================

Checkpoints are one of the most important features.

A checkpoint should capture the actual state of the work.

Include:

Task ID
Original request
Current state
Current Worker
Provider
Model
Attempt history
Files changed
Git information if available
Test results
Browser validation
Errors
Completed work
Remaining work
Current blocker
Recommended next action
Token usage
Cost
Timestamp

Example:

TASK:
Fix authentication

WORKER:
Cloud coding agent

COMPLETED:
Backend authentication fixed.
Database migration completed.

REMAINING:
Frontend login still returns HTTP 500.

TESTS:
18 passed
2 failed

CHECKPOINT:
Backend complete.
Resume frontend authentication debugging.

A different Worker should be able to resume from this checkpoint.

==================================================
CONTEXT MANAGEMENT
==================================================

This is a major product feature.

Do NOT blindly pass the entire conversation history to every Worker.

Supervisor should maintain structured task state.

When switching agents:

provide:

original objective
current state
relevant files
previous changes
test results
current errors
checkpoint
next recommended action

This reduces token consumption.

The Supervisor should be able to summarize old context.

==================================================
BUDGET CONTROL
==================================================

Cloud AI can become expensive.

Supervisor must enforce budgets.

Support:

per-task token budget
per-task cost budget
monthly budget
provider budget
maximum attempts

Example:

Task budget:
$0.50

Cloud Worker consumes:
$0.31

Remaining:
$0.19

Supervisor must prevent spending beyond the configured limit.

Show:

tokens used
estimated cost
actual cost
remaining budget

If the budget is exhausted:

checkpoint the task

and stop or switch to an allowed cheaper Worker.

==================================================
LOCAL-FIRST STRATEGY
==================================================

The system should prefer local Workers when configured.

Example:

Local Worker available:
use local Worker.

Local Worker repeatedly fails:
escalate.

Strong cloud Worker solves difficult portion:
checkpoint.

Cheaper local Worker resumes:
continue.

This allows expensive models to be used only when necessary.

==================================================
VALIDATION
==================================================

A Worker saying:

"Done"

must NOT automatically mean the task is done.

Supervisor should independently validate the result.

Validation can include:

1. Tests
2. Browser
3. Application health
4. Logs
5. Expected output
6. User-defined assertions

Only after validation succeeds should the task become DONE.
